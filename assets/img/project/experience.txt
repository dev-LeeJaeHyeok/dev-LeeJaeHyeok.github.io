1. 개요
 - 농협정보시스템의 월 400만 건 규모의 RCS 문자를 처리하기위해 농협측 서버와 연동하기 위한 시스템 구축을 프로젝트 리더로 담당했었습니다.
 클라이언트 측과 협의된 내용을 바탕으로 고객사의 RCS 문자 발송 요청부터 시작하여 비즈니스 로직, 이동통신사 전송, 결과 리포트 처리까지 모든 흐름을 구현하고, 주요 요구사항이었던, 최대 3,000 TPS 처리 성능과 장애 복구 로직 구현 및 모니터링을 구축했습니다.

2. 아키텍처 고민
 - 자사 시스템이 처리해야할 기능에는 크게 5가지가 존재했습니다.
  (1) 기존 고객사(농협) 시스템에 연동할 발송/리포트 세션 관리
  (2) RCS 문자 전송 요청 수신
  (3) 문자 처리 이력 관리
  (4) 이동통신사 RCS API 연동을 통한 실제 문자 발송
  (5) 문자 처리 결과 전달

  이 외에 요구사항에는
   1. 세션당 20~25TPS 처리성능이 요구됩니다.
   2. 최대 세션은 120개로, Peek Time에 초당 3,000개의 메시지를 처리하는 성능을 확보해야합니다.
   3. 모든 메시지는 유실이 없어야합니다.
   4. 서버는 리포트 데이터를 외부로부터 수신받은 직후 농협정보시스템측 클라이언트에게 3초 이내로 발신되어야합니다.
  등이 있었습니다.

  우선, 하나의 서버에 발송 세션과 리포트 세션 관리와 DB와의 I/O, 이동통신사 API 연동을 통한 문자 발송 및 리포트 전달, 그 외에도 예외 처리 등을 넣기에는 무겁다고 판단했으며, 세션이 서비스 온타임에 증가할 수 있다는 점을 감안하여 MSA 방식을 선택하게됩니다.
  그리고, 현재 속한 개발팀이 주력으로 사용하고있으며 안정적인 버전인 Java 11/Spring 2.7을 사용
  책임과 역할 나누기
  서버를 나누는 기준은 시스템의 핵심 기능을 나누어 해당 역할만 집중할 수 있도록 나누었습니다.
   - 발송 파이프라인의 시작을 담당하며, 고객사의 연결 세션을 관리하는 Receiver 서버
   - 파일 데이터 처리를 위해 메모리와
  또한, 자사에서 운영중이던 RabbitMQ를 활용하여 백엔드 서비스간 통신에 사용하였습니다. 이는 서비스 간 직접적인 호출 관계를 제거하여 결합도를 낮추고, Queue를 통해 순간적인 트래픽을 흡수하며, Consumer의 장애나 처리 지연이 다른 서비스로 전파되는 것을 방지하는 안정성이 있어 채택하게되었습니다.
  RabbitMQ의 도입으로 하나의 이벤트 발행을 통해 수행되어야하는 여러가지 작업을 Topic Exchange 기능으로 여러 서버에 이벤트를 전파하여 비동기 처리할 수 있도록 설정하면 성능 확보와 유지보수 측면에서도 이점이 많을 것으로 판단했습니다.

   (system-arch.png)

  각 서버는 명확한 책임별로 분리되어있었고, 운영중에도 변경사항이 생길때 전체를 수정하는 것이 아니라 관련 부분만 수정하여 변동과 작업을 최소화 할 수 있어 명확한 업무 분배와 업무 부담을 줄일 수 있었습니다.

3. 성능에 대한 고민
   >> 기존 Thread-Per-Connection 방식은 세션마다 Thread를 할당하기 때문에 세션이 늘어날수록 OS가 관리해야 할 Thread도 함께 증가하며, 네트워크 I/O를 기다리는 동안 Thread가 Blocking 상태로 유지되고 처리 구간을 별도의 Thread Pool로 분리하더라도 전체 Thread 수는 증가하게됩니다. 이러한 구조는 Stack Memory 사용량과 Scheduling, Context Switching 비용을 증가시킬 수 있어서 제한된 하드웨어에서 높은 처리량을 확보해야 하는 현재 환경에는 적합하지 않다고 판단했습니다.

   - Solution(그림 첨부해서 다시)
   >> 이를 해결하고자 Java의 고성능 비동기 Non-Blocking 통신 프레임워크인 Netty를 선택했습니다. Netty 공식 문서에 따르면, 하나의 EventLoop가 여러 Channel을 처리하고, NioEventLoop가
     Selector 기반의 I/O Multiplexing으로 동작한다는 점을 통해서 서버당 최대 120개의 세션(Channel)을 소수의 EventLoop Thread가 처리하므로 OS의 Thread Scheduling과 Context Switching 부담을 줄일 수 있어서 요구사항에 적합하다고 판단했습니다.

4. 개발
   (1) Receiver - java 11, Spring Boot 2.7.x, Netty 4.1.x, Spring Amqp
     - 클라이언트와의 통신을 위한 프로토콜은 메시지 길이와 타입을 알 수 있는 Header와 상세 내용이 들어있는 Body로 사전에 필드명과 데이터가 정의되어있던 Byte단위로 데이터를 읽었으며, ChannelHandler 작성으로 각 프로토콜 메시지 타입에 따른 처리와 세션에서 발생할 수 있는 예외처리 로직을 작성했습니다.
   (2) Sender - java 11, Spring Boot 2.7.x, Spring Amqp
     - 실제 RCS 문자를 전송하기위해 이동 통신사가 제공하는 RCS 처리 API를 사용하는 클라이언트입니다.
   (3) Storage - java 11, Spring Boot 2.7.x, Spring Amqp
     - 파일 업로드와 다운로드 API를 제공하고, 파일 정보를 DB로 관리하는 파일 서버이며 RCS의 첨부파일은 이동통신사에 첨부파일을 등록하고 사용하는 방식으로, 처리 비용이 MD5보다 비교적 크더라도 문자 서비스 특성상 무결해야하기 때문에, 중복 파일 방지를 위한 암호화 해시 알고리즘 SHA-256로 파일 중복처리를 구현했습니다. 클라이언트의 파일 업로드 요청 시 로컬에 파일을 기록하고, 이동통신사 측 API를 사용하여 파일을 등록하는 흐름을 작성했습니다.
   (4) DB Logger - Spring Boot 2.7.x, Spring Amqp, JDBC, MariaDB
     - 메시지 처리 이력을 관리하는 서버입니다. 주로 메시지 전송 요청 이벤트를 수신하여 이력을 남기고, 전송된 메시지의 처리 결과 이벤트가 들어오면 업데이트하는 서버입니다.
   (5) Reporter - java 11, Spring Boot 2.7.x, Spring Amqp
     - 메시지 처리 결과 이벤트를 수신하여 클라이언트로 전송하는 서버입니다. 프로토콜 메시지 타입에 따른 처리를 위해 ChannelHandler로 비즈니스로직을 작성하고, 세션에 대한 끊김, 중복접속 등 방어로직을 작성하였습니다.
   (6) Dummy Client - java 11, Spring Boot 2.7.x, Netty 4.1.x
     - 농협정보시스템의 클라이언트를 모방하여 만든 내부 테스트용 서버입니다. 주로 테스트 시 사용됩니다.
   (7) Dummy Gateway - java 11, Spring Boot 2.7.x
     - 이동 통신사의 RCS 처리 API를 모방하여 만든 내부 테스트용 서버입니다.
   (8) 공통
     - 메시지 유실 방지를 위한 RabbitMQ를 통한 이벤트 발행 및 소비전략
           실제 문자 메시지를 처리하는 서비스인 만큼 메시지가 어느 구간에서도 사라지지 않아야 했기 때문에,
           발행과 소비 양쪽에 각각 확인 절차를 두었습니다.

          (Spring Boot 서버가 RabbitMQ로 이벤트를 발행하는 사진 png)
           발행 시에는 Publisher Confirm을 적용했습니다. 클라이언트로부터 메시지 전송 요청을 수신하면
           이벤트를 발행하고, 브로커가 해당 메시지를 정상적으로 수신했다는 confirm을 받은 뒤에
           클라이언트에게 응답 전문을 전송하도록 구성했습니다. 응답을 먼저 보내는 경우 브로커 장애나
           네트워크 문제로 발행에 실패하면 클라이언트는 접수된 것으로 알고 있지만 실제로는 처리되지 않는
           구간이 생기기 때문입니다.

          (RabbitMQ의 이벤트를 소비하여 처리하는 사진 png)
           소비 시에는 acknowledge-mode를 manual 모드로 하여, 메시지를 수신한 시점이 아니라 비즈니스
           로직이 완료된 시점에 ack를 전송하도록 구현하였습니다. 처리 도중 서버가 종료되더라도 ack가
           전달되지 않은 메시지는 Queue에 그대로 남아있기 때문에, 재기동 이후 해당 메시지부터 다시
           처리할 수 있습니다. 재처리 과정에서 동일한 메시지가 다시 유입될 수 있으나, 이는 아래의
           Redis 기반 멱등 처리로 방어됩니다.
     - 클라이언트의 메시지 중복 처리를 방지하기 위해 Redis의 SET NX EX를 활용했습니다.
     (message-key_DUP.png)
      클라이언트 식별 Key + 메시지 식별 Key를 조합하여 메시지마다 독립적인 Redis Key를 생성하고, NX 옵션을 통해 동일한 Key가 존재하는 경우 중복 요청으로 판단하도록 구성했습니다.
      각 Key에는 1시간의 TTL을 적용했습니다. 피크 타임에 최대 3,000 TPS가 발생하더라도 1시간 동안 최대 1,080만 개의 Key가 존재할 수 있다는 점을 고려하여 해당 시스템에서 사용할 수 있는 Redis의 메모리를 계산하였습니다.

5. 테스트
  - 기능 테스트
    > 내부적으로 메시징 플랫폼에서 처리하는 기본적이지만 중요한 전송 기능, 이력 관리, 파일 관리, 중복 방지, 유실 방지 등, 모든 흐름에 대한 테스트 케이스를 작성하고 진행했습니다.
  - 성능 테스트
    > 개발된 Dummy Client를 사용하여 내부 시스템에 부하를 주어 Grafana, JMC 등을 사용하여 시스템 성능을 검증하였습니다.
    > 환경 : (하드웨어는 Client 1, Receiver 1, Reporter 1, Sender 1, DB Logger, Dummy Gateway 1대가 있고, 스펙은 4core 8G memory)
    > 테스트 측정 : TPS 및 리포트 전달 속도 측정
    > 목표 : 3000TPS, 리포트 발생 후 3초 이내 클라이언트에게 도달
    > 결과 : 부하 시 메시지 처리 파이프라인관련 서버들의 Memory 누수 현상 없음, CPU 최대 42% ~ 58% 사용으로 3000TPS 달성, 리포트 전달 속도 1초 이내 달성
  - 장애 테스트
    > 성능 테스트 도중 특정 서버를 프로세스를 정상종료, 강제종료하였을 때, 정상처리 및 재처리를 수행하는지 안정성을 검증하였고, 마찬가지로 테스트 케이스를 작성했습니다.
    > 정상 종료 테스트
      (1) 테스트 클라이언트를 통해 부하를 발생시킨 뒤, 사전에 작성해둔 서버 프로세스를 종료시키는 쉘 스크립트 파일을 실행시켜 서버 순서대로, 랜덤으로 종료시킨다.
      (2) 이후 종료되었던 서버를 재기동하여, 메시지 유실없이 재처리하고, 클라이언트에게 정상적으로 리포트 전문을 모두 전송하였는지 확인한다.
    > 강제 종료 테스트
      (1) 테스트 클라이언트를 통해 부하를 발생시킨 뒤, 사전에 작성해둔 서버 프로세스를 강제 종료(kill -9)시키는 쉘 스크립트 파일을 실행시켜 서버 순서대로, 랜덤으로 종료시킨다.
      (2) 이후 종료되었던 서버를 재기동하여, RabbitMQ를 기반으로한 메시지 유실 방지 로직과 중복 처리가 정상적으로 수행되었는지 확인한다.
    > 테스트 결과
      - 유실 0건, 중복 0건

6. 모니터링 구축
  Spring Actuator로 서버를 모니터링 하기위한 기본적인 매트릭외에 비즈니스 관련 매트릭을 생성하여 Prometheus, Grafana를 사용해 대쉬보드를 구축하고, Prometheus AlertManager를 사용하여 에러상황 발생시 Slack으로 알람을 보낼 수 있게 구축하였습니다.
